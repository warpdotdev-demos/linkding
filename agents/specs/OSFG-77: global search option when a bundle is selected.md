# Spec: global search option when a bundle is selected

**Ticket:** [OSFG-77](https://warp-se-demo.atlassian.net/browse/OSFG-77) · **Estimate:** L (5) · **Target repo:** `warpdotdev-demos/linkding` (base `master`)
**Originating thread:** [Slack #all-warp-se-demos](https://warpsedemos.slack.com/archives/C0AR8VDCU1H/p1785854812509079) · **Requester:** Killian (`pkillianjackson`)
**Code references are pinned to** `fdd4234bb40108b6c87f9ed8fecb332c3f754a2a`.

Request, verbatim:

> let's add a global search option. When a bundle is selected and the search bar is used, the search is performed only within the elements of that bundle. Users will have a bundle called "favorites" for example containing the links they use most and many users set a bundle as their homepage. This makes it tedious to go back to the main page every time to perform a search.

## == PRODUCT ==

**Summary:** While a bundle is selected, linkding always ANDs the search query with the bundle's filter, so there is no way to search the whole collection without first deselecting the bundle — painful for users whose landing view is a bundle. Add an explicit, per-search **scope** control: keep the bundle selected, but let the user widen the current search to *all* bookmarks with one click, from the search bar or from the (currently misleading) empty state.

**Key design choices:**
1. **Scope is a URL param, not a preference.** A new optional `scope=all` query param widens the search; absent (or `scope=bundle`) preserves today's behavior exactly. No `UserProfile.search_preferences` entry, no migration, no session state — the URL fully describes the view, so results stay shareable and bookmarkable, and global search can never silently become someone's default.
2. **The bundle stays selected; only the search widens.** `bundle=<id>` remains in the URL and the bundle stays highlighted in the side panel. Deselecting the bundle instead would make this feature identical to the already-existing "click another bundle / go back to /bookmarks" flow, and would lose the user's place.
3. **One scope for the whole page.** The result list, the tag cloud, pagination links and the bulk-action target set all reflect the same scope. A page where results are global but the tag cloud is bundle-scoped is actively confusing.

**Behavior** (numbered, testable invariants):
1. **Default unchanged.** With a bundle selected and no `scope` param, the bookmark list is the intersection of the search query and the bundle's filter — byte-identical to today.
2. **Global scope widens the search.** With `bundle=<id>&q=<term>&scope=all`, the list contains every bookmark of the view (active / archived / shared) matching `<term>`, including bookmarks the bundle excludes.
3. **The bundle stays selected.** In global scope, `bundle=<id>` is still in the URL and the bundle entry in the side panel is still rendered as selected. Returning to bundle scope (dropping `scope`) restores the bundle-scoped result list with the same query.
4. **Discoverable control at the search bar.** Whenever a bundle is selected, the search area renders a scope control that shows the active scope and offers the other one:
   - bundle scope → label naming the bundle (e.g. `In favorites`) plus an action `Search all bookmarks`;
   - global scope → label `All bookmarks` plus an action to go back to the bundle (e.g. `Back to favorites`).
   Both actions are plain `GET` links that preserve every other query param (`q`, `sort`, `unread`, `shared`, `user`, `modified_since`, `added_since`, `bundle`) and drop `page` and `details`. No JavaScript is required for the control to work.
5. **Scope is legible.** From the page alone the user can tell which scope the current result list reflects (invariant 4's label is the single source of that signal).
6. **Scope survives interaction.** Submitting a new query from the search bar, paginating, clicking a tag in the tag cloud, or firing a bulk action all keep the active scope (`scope=all` is carried as a hidden form field and in generated URLs).
7. **One scope per page.** In global scope the tag cloud lists tags of the widened result set, and bulk actions apply to the widened query set. In bundle scope both stay bundle-scoped.
8. **Shareable.** Reloading or sharing the URL reproduces exactly the same result set and control state.
9. **Honest empty states.** The empty area under the search bar renders exactly one of three states:
   a. **invalid query** — unchanged from today;
   b. **no results** — shown whenever any narrowing filter is active (`q`, `bundle`, `unread`, `shared`, `user`, `modified_since`, `added_since`): a "no results" message, and — when a bundle is selected *and* the scope is bundle — an escape-hatch link `Search all bookmarks` pointing at the same query with `scope=all`;
   c. **first run** — the existing "You have no bookmarks yet" copy with the add/import/extension links, shown *only* when no narrowing filter is active. `sort` and `scope` do not count as narrowing filters.
10. **Never a default, never persisted.** "Save as default" in the search-options popover does not persist `scope` (it is not a preference), and no code path defaults it to `all`.
11. **Adjacent consumers unaffected.** The RSS feeds ignore `scope` entirely (they build `BookmarkSearch` explicitly). The REST API's behavior is unchanged when `scope` is absent; when a client passes `scope=all` alongside `bundle`, it widens identically to the UI (documented). An unrecognized `scope` value falls back to bundle scope rather than erroring.

**Explicitly out of scope:** persisting the choice as a user preference; changing how bundles are selected or created; changing search-autocomplete suggestions (they are already unscoped — they never send `bundle` — see `bookmarks/frontend/components/search-autocomplete.js:174-186 @ fdd4234`); the pre-existing behavior of `?bundle=<id>` on the public (anonymous) shared page.

## == TECH ==

**Context — how scoping works today:**
- `BookmarkSearch` declares its URL params, defaults and preferences and resolves them from the request: `bookmarks/models.py:238-343 @ fdd4234`. `bundle` is resolved to a `BookmarkBundle` owned by the user (`bookmarks/models.py:334-337`); `query_params` (`:311-320`) emits only *modified* params, which is what every generated URL is built from.
- The bundle filter is applied in exactly one place: `if search.bundle: query_set = _filter_bundle(...)` in `_base_bookmarks_query` — `bookmarks/queries.py:267-269 @ fdd4234`. All three list views (`query_bookmarks`, `query_archived_bookmarks`, `query_shared_bookmarks`, `bookmarks/queries.py:33-56`) and all three tag-cloud queries (`query_bookmark_tags` and siblings, `bookmarks/queries.py:305-336`) route through it, so a single change covers list + tag cloud + archived + shared.
- `BookmarkSearchForm.__init__` iterates `search.params`, sets each field's initial value, and renders every *modified, non-editable* param as a `HiddenInput` — `bookmarks/forms.py:291-303 @ fdd4234`. This is why `bundle` is re-submitted by the search bar, and it is also the mechanism that will carry `scope` through a search submit. **Every name in `BookmarkSearch.params` must have a matching form field**, so adding a param requires adding a field here.
- URL generation is param-preserving already: `RequestContext.query_params = request.GET.copy()` (`bookmarks/views/contexts.py:42 @ fdd4234`) backs `get_url` / `index()` / `action()` (`:55-72`), the tag links (`AddTagItem` / `RemoveTagItem`, `:291-393`) and the bulk-action form URL (`BookmarkListContext.action_url`, `:225`); the pagination tag copies `request.GET` too (`bookmarks/templatetags/pagination.py:19-21`). **A new query param is therefore preserved by tag links, pagination and bulk actions for free** — only the search-bar form (hidden field) and the new controls need explicit work.
- The search bar template gets a *fixed* context dict from the `bookmark_search` inclusion tag (`bookmarks/templatetags/bookmarks.py:9-27 @ fdd4234`) — `request`, `search`, `search_form`, `preferences_form`, `mode`. Anything the chip needs must be added there. Template: `bookmarks/templates/bookmarks/search.html:1-15 @ fdd4234`.
- The empty state is a single include with only an invalid-query branch and a first-run branch: `bookmarks/templates/bookmarks/empty_bookmarks.html:1-16 @ fdd4234`, rendered from `bookmarks/templates/bookmarks/bookmark_list.html:2-3` when `bookmark_list.is_empty`.
- Side-panel selection is derived from the raw request (`BundlesContext`, `bookmarks/views/contexts.py:645-662 @ fdd4234`), so the highlight persists automatically as long as `bundle` stays in the URL.
- Feeds construct `BookmarkSearch(...)` field-by-field (`bookmarks/feeds.py:39-44 @ fdd4234`) → unaffected. The API builds it via `from_request` (`bookmarks/api/routes.py:61 @ fdd4234`) → the param is honored there, opt-in only.

**Design alternatives:**
- **Param shape.** (a) *Scope enum* `scope=bundle|all` — selected: matches the existing string-enum idiom (`FILTER_UNREAD_OFF/YES/NO`), reads well in a URL, and leaves room for future scopes; costs one extra constant set. (b) Boolean-ish `global=yes` — smaller, but a bare boolean named after the *exception* reads poorly and doesn't extend. (c) Reuse `bundle` by emptying it (`bundle=`) — rejected: it destroys the selected-bundle state (violates invariant 3) and is indistinguishable from "no bundle".
- **Where the bundle filter is skipped.** (a) *In `_base_bookmarks_query`, guarded by a `BookmarkSearch` property* — selected: one line, one place, inherited by list + tag cloud + archived + shared + API, and `search.bundle` stays populated so the UI can still name the bundle. (b) In `BookmarkSearch.from_request` (drop the bundle when the flag is set) — rejected: `search.bundle` becomes `None`, so `query_params` drops `bundle`, the hidden field disappears and the side-panel highlight is lost (violates invariants 3 and 6). (c) In the form / template only — rejected: doesn't change the query at all.
- **The control's form.** (a) *Plain `GET` links in the search area* — selected: works without JS, is instantly shareable, and needs no changes to the Lit component. (b) A radio/toggle inside the existing search-options popover — rejected as the *only* affordance (too buried for a mid-search action, per the requester's alignment answers); the always-visible control plus the empty-state hatch covers the workflow. (c) A JS toggle rewriting the query string — rejected: extra client complexity for no gain.
- **Distinguishing "no bookmarks at all" from "no results".** (a) *A `has_filters` property on `BookmarkSearch`* — selected: modified-param logic already exists (`is_modified`), and excluding `sort`/`scope` keeps sorting an empty collection from producing a misleading "no results". (b) Compare against an unfiltered `count()` — rejected: an extra query per empty render. (c) Test `search.q` only — rejected: misses the bundle-only and unread/shared-only cases, which is precisely the reported confusion.

**Proposed changes** (implementation-ready; file references pinned as above):

1. `bookmarks/models.py` — `BookmarkSearch`:
   - add constants `SCOPE_BUNDLE = "bundle"` and `SCOPE_ALL = "all"`;
   - append `"scope"` to `params` and `defaults["scope"] = SCOPE_BUNDLE`; **do not** add it to `preferences`;
   - accept `scope: str = None` in `__init__` and normalize unknown values to the default (`self.scope = scope if scope in (SCOPE_BUNDLE, SCOPE_ALL) else self.defaults["scope"]`);
   - add `applies_bundle_filter` → `bool(self.bundle) and self.scope != SCOPE_ALL`;
   - add `FILTER_PARAMS` (every param except `sort` and `scope`) and `has_filters` → `any(self.is_modified(p) for p in FILTER_PARAMS)`.
   `from_request` needs no change (the generic string branch handles it).
2. `bookmarks/queries.py:267-269` — replace `if search.bundle:` with `if search.applies_bundle_filter:`. This is the whole behavioral change; list views, tag clouds, archived, shared and the API inherit it.
3. `bookmarks/forms.py` — `BookmarkSearchForm`: add `SCOPE_CHOICES` and a `scope = forms.ChoiceField(choices=SCOPE_CHOICES, required=False)` field so the `search.params` loop finds it; it is never listed in `editable_fields`, so a modified `scope` renders as a `HiddenInput` and survives search-bar and preferences submits. Do not add it to the preferences forms in `bookmarks/templatetags/bookmarks.py` (invariant 10).
4. `bookmarks/utils.py` — add one shared helper used by both new controls, e.g. `def scope_url(request, scope: str | None) -> str`: copy `request.GET`, drop `page` and `details`, set `scope` (or remove it for bundle scope), and return `request.path` + encoded query. Keeping this in Python (rather than a template tag) makes both call sites identical and unit-testable.
5. `bookmarks/templatetags/bookmarks.py` — in `bookmark_search`, add `scope_all_url` and `scope_bundle_url` (via `utils.scope_url`) to the returned context.
6. `bookmarks/templates/bookmarks/search.html` — inside `.search-container`, when `search.bundle` is set, render the scope control per invariant 4 (label + link). Keep it inside the existing header controls so the responsive layout in `bookmarks/styles/responsive.css` still collapses cleanly.
7. `bookmarks/styles/bookmark-page.css` (near `.bookmarks-page .search-container`, line 48) — style the control as a compact chip, reusing the existing selected-pill idiom from `bookmarks/styles/bundles.css`; must be legible in both the light and dark themes.
8. `bookmarks/views/contexts.py` — `BookmarkListContext.__init__`: add `self.has_filters = search.has_filters`, `self.bundle = search.bundle`, `self.show_global_search_hint = search.applies_bundle_filter`, and `self.scope_all_url = utils.scope_url(request, BookmarkSearch.SCOPE_ALL)`. No change is needed for tag links, pagination or `action_url` (they copy `request.GET`).
9. `bookmarks/templates/bookmarks/empty_bookmarks.html` — restructure into the three branches of invariant 9, driven by `bookmark_list.query_is_valid`, `bookmark_list.has_filters` and `bookmark_list.show_global_search_hint` (escape-hatch link → `bookmark_list.scope_all_url`, naming the bundle).
10. `docs/src/content/docs/api.md` — after the `bundle` bullet (line 40), document `scope` (`bundle` default / `all` to ignore the bundle filter) for the bookmark list endpoints.

No model/DB migration. No changes to `bookmarks/feeds.py`, `bookmarks/api/routes.py`, or the Lit components.

**Open questions resolved** (all from the requester's alignment reply "go with your leans", plus codebase findings):
- *Where the option lives* → both an always-visible scope control next to the search bar **and** an escape hatch in the no-results state (invariants 4 and 9b).
- *Per-search vs. persisted* → per-search, URL param only; no `search_preferences` entry, no migration, no session stickiness (invariant 10).
- *Bundle selected or cleared* → stays selected; only the search widens (invariant 3).
- *Tag cloud / bulk actions* → follow the widened scope; one scope per page (invariant 7).
- *Archived and shared views* → parity, for free via `_base_bookmarks_query` (invariant 2).
- *Misleading first-run empty state* → fixed in this PR, and it hosts the escape hatch (invariant 9).
- *Hard no's* → global search is never the default; the bundle selection is never silently lost; feeds unaffected and the API unchanged when the param is absent (invariants 3, 10, 11).
- *Does the search autocomplete need the param?* → No. It sends only `user`, `shared`, `unread`, `q` (`search-autocomplete.js:174-186`), so its suggestions are already unscoped; leaving it untouched is both minimal and consistent.
- *Do generated URLs need per-site work?* → No. Tag links, pagination and the bulk-action URL copy `request.GET`, so they carry `scope` automatically; only the search form (hidden field) and the two new controls are explicit.
- *Invalid `scope` values* → normalized to bundle scope in `BookmarkSearch.__init__` (invariant 11), so junk never reaches generated URLs or hidden fields.
